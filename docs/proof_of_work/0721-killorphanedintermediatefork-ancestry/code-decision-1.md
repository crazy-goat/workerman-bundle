# Code decision 1 — issue #721: `killOrphanedIntermediateFork()` fingerprint path never fires in daemon mode

## Approach

Extended `ProcessInspector::killOrphanedIntermediateFork()` in `src/ProcessInspector.php` to verify **ancestry** instead of identity for the daemonize intermediate.

The production daemon flow is: launcher forks intermediate, intermediate forks master and is supposed to exit, master survives. `ServerManager::stop()` captures `parentPid = getParentPid(masterPid)` (the intermediate) **before** killing the master, then calls `killOrphanedIntermediateFork(parentPid, fingerprint)` after the master is dead to clean the hung intermediate (grpc `grpc_shutdown()` hangs on macOS). The fingerprint is written by the master itself (`MasterWorker::saveMasterPid()`), so `fingerprint->pid == masterPid`, never the intermediate's. The old branch `matchesFingerprint(parentPid, fingerprint)` required `parentPid === fingerprint->pid` and therefore always refused in the production daemon call flow; only unit tests that passed the master PID itself exercised it. The legacy `/proc` cmdline fallback was unreachable because the fingerprint file always exists after `start -d`.

New logic keeps the direct identity path for backward compat and for the non-daemon case, and adds an ancestry path:

1. **Direct identity**: `matchesFingerprint(parentPid, fingerprint) === true` → `SIGKILL`. Covers tests where parentPid is the master itself and any future direct-match use.
2. **Ancestry**: `getParentPid(fingerprint->pid) === parentPid` → the parent is the recorded parent of the fingerprinted master. Only then, verify the parent looks like a Workerman master via `isWorkermanMasterTitle(parentPid)` (`/proc/$pid/cmdline` contains `"WorkerMan: master process"`). If the title check passes → `SIGKILL` the intermediate. If ancestry matches but the title check fails → fail closed with a warning (this is the non-daemon shell path: the shell is the parent of the master but its cmdline does not contain the Workerman title, so it is not killed). If neither identity nor ancestry matches → fail closed with a warning.
3. **Legacy fallback** (no fingerprint): now delegates to the same `isWorkermanMasterTitle()` helper.

A new private helper `isWorkermanMasterTitle(int $pid): bool` encapsulates the `/proc` cmdline title check, mirroring the legacy fallback's tightened check (issue #584): only the actual Workerman master title, not any `"WorkerMan"` substring, qualifies. The method fails closed on unreadable cmdline.

`ServerManager` was not changed: `parentPid` is already captured before `posix_kill(master)` while the master is still alive, so `getParentPid(fingerprint->pid)` after the master becomes a zombie still reads the same PPid via `/proc` (zombie retains its `/proc` entry until reaped). Re-reading inside `killOrphanedIntermediateFork()` is therefore valid while the intermediate remains the zombie's parent. If `/proc` has already been reaped (master fully gone, no `/proc` entry), `getParentPid` returns `0` and the ancestry check fails closed — safe, though the intermediate then leaks (same as before, but now only when the kernel has already reaped the master).

Two new Linux-only integration tests in `tests/ProcessInspectorTest.php` pin the two ancestry branches:

- `testKillOrphanedIntermediateForkWithFingerprintKillsParentViaAncestryOnDaemon`: builds a real parent→child pair via `forkAncestryPair(true)` where the parent is exec'd with `WorkerMan: master process` title, captures the child's fingerprint, asserts `getParentPid(child) === parent`, calls `killOrphanedIntermediateFork(parent, fingerprint(child))`, and asserts the parent dies while the child (reparented to init) stays alive. Helper `forkAncestryPair()` creates the hierarchy via a temporary PHP script that forks inside the Workerman-titled parent, communicating PIDs via marker files and `Wait::until`.
- `testKillOrphanedIntermediateForkWithFingerprintDoesNotKillNonWorkermanParentViaAncestry`: same hierarchy but `forkAncestryPair(false)` creates a plain parent without the Workerman title; ancestry matches but the title check must refuse, so the parent stays alive.

Both helpers clean up with `SIGKILL` and `pcntl_waitpid`/`Wait::until`, and unlink temporary script/marker files. On Darwin these tests are skipped (`@requires OS Linux`) — the early `if (!isLinux()) return;` still makes the whole method a no-op there (issue #722 adds `ps`-based support separately).

## What I rejected

- **Changing `ServerManager::stop()` to pass the master PID explicitly or to record the intermediate PID at start time.** Passing `masterPid` would make the ancestry check more explicit but widens the API for a single caller; using `fingerprint->pid` as the master PID is equivalent and keeps the method self-contained. Recording the intermediate PID at start (e.g. a sidecar file written before `daemonize()`) would require plumbing through `Runner`/`MasterWorker` and handling the case where the launcher PID is not the intermediate's parent after the double fork — more surface for a two-line fix.
- **Reusing `matchesFingerprint()` for the zombie master.** `matchesFingerprint()` fails closed via `isProcessAlive()` (zombie → not alive → false), so it cannot verify the master after `waitForProcessToStop()` succeeds. Adding a zombie-tolerant fingerprint check (compare `startTime`/`uid` via `/proc` without liveness) would be more code and would duplicate `MasterFingerprint::readStartTimeForPid`/`readUidForPid` logic already implicit in the fingerprint capture. The chosen fix trusts the fingerprint that `getRunningMasterPid()` already verified while the master was alive, and only verifies the parent-child edge plus the parent's title.
- **Adding `ps`-based `getParentPid()` for non-Linux in this issue.** That is issue #722's scope. Keeping the `!isLinux()` early return here keeps the diff minimal and the ancestry logic Linux-only; a follow-up will add `ps -o ppid=` and drop the early return once the ancestry model exists.
- **Making `isWorkermanMasterTitle()` public or exposing it for mocking.** It is a private predicate; tests verify it indirectly via the kill behaviour, which is the security-relevant property.

## What was uncertain

- **Whether `getParentPid()` for a zombie master still returns the intermediate.** On Linux a zombie retains `/proc/$pid/status` with `PPid` until its parent reaps it, and the hung intermediate never reaps, so the entry stays readable at `killOrphanedIntermediateFork()` time. This was not probed live on Linux in this session (host is Darwin); CI on Linux will be the real proof. If the kernel had already reaped the zombie before the kill, `getParentPid` would return `0` and the ancestry check would fail closed (intermediate leaks once), which is safe but not ideal. An alternative would have been to capture `parentPid` as the ancestry proof itself (the value already passed in), but that would be a tautology.
- **Whether `cli_set_process_title()` is a viable alternative to `exec -a` for the title helper.** Prior work (issue #584, `forkChildWithMasterTitle`) found it unreliable on PHP ≥8.5 (original argv kept on some builds), so the test helper uses `exec -a 'WorkerMan: master process ...' php ...` as before — kernel behaviour, identical everywhere.
- **PID reuse risk for the fingerprint.** The fingerprint is verified by `isMasterRunning()` seconds before the kill, and the window between `posix_kill(master)` and `killOrphanedIntermediateFork()` is short; a full PID wrap reusing the same PID with a different `startTime`/`uid` in that window is negligible. No extra `startTime` recheck was added after the master's death for that reason.
